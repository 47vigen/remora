# remora: a management MCP server (research)

Date: 2026-10-16. Status: research, nothing built. remora tree read at `the remora tree`.

## 0. What remora already has (the facts the design rests on)

- One listener, one mux: `cmd/remora/serve.go:200` mounts `/api/` (management), `:207` `/v1/` (proxy), `:209` `/` (web UI).
  `/mcp` would be one more `mux.Handle` line; it is more specific than `/`, so it wins over the SPA.
- Management API: `api/openapi.yaml`, about 45 operations (providers, accounts + OAuth logins, aliases + compile/chain,
  cooling, client keys + usage, logs + live WebSocket, stats, settings password, API tokens, config export/plan/apply).
  Generated strict server in `internal/api/gen`; a generated **client** (`gen.ClientWithResponses`) already exists and the
  CLI uses it (`cmd/remora/client.go:33-63`).
- Auth (`internal/auth/session.go:120-141`): a request is the admin if it carries the `remora_session` cookie **or**
  `Authorization: Bearer rmt_…`, an API token created in Settings (`internal/auth/token.go:26-45`; sha256 stored,
  value shown once). There are no scopes or roles: a token is full admin. `Middleware` also applies
  `http.CrossOriginProtection` (`internal/auth/middleware.go:21-45`); bearer clients send no Origin and pass.
- The CLI already reads `REMORA_URL` + `REMORA_TOKEN` (`cmd/remora/client.go:20-23`).
- Declarative config: `internal/config`. `File{Providers, Aliases, Keys}` (`file.go:19-59`); accounts are NOT in it
  (Change kinds are `provider|alias|key`, `openapi.yaml:1641`). `Plan` changes nothing; **with `prune=false`
  nothing is deleted, not even a provider key the document leaves out** (`plan.go:46-51`). So a partial document applied
  with `prune=false` is an upsert of exactly the resources it names. Secrets are `env:NAME`; an absent NAME keeps the
  stored secret (`plan.go:47-49`). A new client key without a value gets a generated one, returned once (`file.go:52-53`).
  `remora apply` is plan-then-`--yes` (`cmd/remora/apply.go:17-80`) with `--prune` defaulting to true.

## 1. OmniRoute: yes, it ships a self-management MCP server

Source: sparse clone at commit `ddf2759e` (2026-10-16) locally, plus
https://cdn.jsdelivr.net/gh/diegosouzapw/OmniRoute@main/docs/frameworks/MCP-SERVER.md (v3.8.51). Not run.

- **Size:** ~110 tools (doc headline; `open-sse/mcp-server/toolCount.ts` computes it). Groups: essential (14: health,
  list/switch/create combo, check quota, cost report, model catalog, route a request, web search/fetch…), advanced (11:
  simulate/explain route, set routing strategy, budget guard, resilience profile, provider metrics, db health, pricing
  sync), cache (2), compression (13), proxy pool (3), memory (3), skills (4), Notion (6), Obsidian (22), plugins (8),
  gamification (8), local corpus (3). Files: `open-sse/mcp-server/tools/*.ts`.
- **Transport:** stdio (`omniroute --mcp`), legacy SSE (`/api/mcp/sse`), Streamable HTTP (`/api/mcp/stream`),
  **stateful** sessions (`httpTransport.ts:93-110`, `sessionIdGenerator: randomUUID`). HTTP transports off by default.
- **Auth:** loopback-only by default; remote needs `Authorization: Bearer <api-key>` whose key has the `manage` scope
  (MCP-SERVER.md:57-75). Per-tool scopes (`read:health`, `write:combos`…) exist but enforcement is **off unless**
  `OMNIROUTE_MCP_ENFORCE_SCOPES=true`. Audit table `mcp_tool_audit`.
- **Implementation:** tools call OmniRoute's own HTTP API through one hop, `omniRouteFetch`
  (`open-sse/mcp-server/internalFetch.ts:1-93`), forwarding the HTTP caller's credential; the env API key is a
  stdio-only fallback. Its header comment documents a real privilege-substitution bug they had when the hop fell back to
  the server key for a remote caller. Lesson for remora: forward the caller's token, never a server credential.
- **No `readOnlyHint`/`destructiveHint` anywhere** in `open-sse/` (grep: zero hits). Destructive tools
  (`omniroute_cache_flush`, `omniroute_memory_clear`, `omniroute_db_health_check` with repair) are only scope-labelled.
- **Symptoms of bloat:** they had to add `toolSearch/register.ts` (a tool to find tools) and `descriptionCompressor.ts`
  (compress tool descriptions to save tokens). Both exist only because 110 tools overflow agent context.

Useful for remora: check quota, list combos (= aliases) with metrics, switch/simulate/explain route (= alias
compile/chain), provider test, cost report (= stats), health. Noise: web search/fetch, Notion, Obsidian, memory, skills,
plugins, gamification, compression/CCR, proxy pool, `route_request` (an agent already has `/v1`), tool search,
description compression.

## 2. Other gateways and well-regarded "operate this service" MCPs

| Product | Self-management MCP? | Notes |
|---|---|---|
| LiteLLM | Yes, **Enterprise only**: LiteAdmin MCP at `/admin/mcp` (1.106+), env `LITELLM_ENABLE_ADMIN_MCP` | Auth = a personal virtual key of a `proxy_admin` user (401/403 otherwise). Tools are a reviewed list (`operations.json` in BerriAI/litellm-admin-mcp) e.g. `list_keys`, `list_teams`, plus meta tools `describe_admin_tool`, `read_admin_result`. `LITELLM_ADMIN_READ_ONLY=true` and a `LITELLM_ADMIN_TOOLS` allowlist. No retries on writes. https://docs.litellm.ai/docs/proxy/liteadmin_mcp_enterprise . Its OSS `/mcp` is a tool **gateway**, unrelated. |
| Bifrost | No | `/mcp` aggregates *connected* MCP servers' tools for clients (gateway), not admin. https://docs.getbifrost.ai/mcp/gateway |
| Portkey | No official one | Two community "portkey-admin-mcp" servers with 150+ tools, domain filter to load subsets; one is in maintenance mode after the Palo Alto acquisition. https://glama.ai/mcp/servers/CodesWhat/portkey-admin-mcp |
| CLIProxyAPI | No | Only third-party servers that *consume* it. |

Tool-design patterns worth copying:

- **Cloudflare code mode** (https://blog.cloudflare.com/code-mode-mcp/): two tools, `search(code)` over the full OpenAPI
  spec and `execute(code)` against `cloudflare.request()`, run in a sandboxed isolate; ~1k tokens of tool definitions for
  2,500 endpoints. Right for a huge API; wrong for remora's 45 operations (needs a JS sandbox; loses per-tool
  annotations; write safety rests only on token scope).
- **GitHub MCP** (https://github.com/github/github-mcp-server): consolidated tools with a `method` enum
  (`issue_read` get/get_comments/…, `issue_write` create/update), **read and write split into separate tools** so each
  keeps honest annotations; `--toolsets`, `--tools`, and `--read-only` which wins over everything. Structured output
  only for protocol ≥ 2026-07-28.
- **Grafana MCP** (https://github.com/grafana/mcp-grafana): categories toggled by `--disable-<category>`;
  `--disable-write` drops all writes; stdio default, `streamable-http` for remote; `--server-auth-token` requires a
  bearer and it logs a security error if a non-loopback server has none.
- **Consolidation consensus**: one-tool-per-endpoint generated from OpenAPI degrades tool choice (Archestra
  https://archestra.ai/blog/thin-mcp-vs-fat-mcp ; Amplitude cut cohorts from 9 tools to 1 while keeping each action's
  permission level https://amplitude.com/blog/lessons-from-consolidating-our-mcp-server.md).

Takeaway: ~10-12 task-shaped tools, read/write split, `method`/`kind` enums inside, honest annotations, a read-only
switch. Don't generate one tool per endpoint.

## 3. Go implementation

- **Official `github.com/modelcontextprotocol/go-sdk` v1.8.0** (2026-09-14; downloaded and read from module cache).
  `go 1.25` (remora is on 1.27). Deps added: `google/jsonschema-go`, `golang-jwt/jwt/v5`, `x/oauth2`, `x/time`,
  `segmentio/encoding`, `yosida95/uritemplate`.
  - `mcp.NewServer(impl *Implementation, opts *ServerOptions) *Server` (`mcp/server.go:211`)
  - `mcp.AddTool[In, Out any](s *Server, t *Tool, h ToolHandlerFor[In, Out])` (`server.go:603`); handler
    `func(ctx, *CallToolRequest, In) (*CallToolResult, Out, error)` (`tool.go:57`). Input and output JSON Schemas
    are inferred from the Go types; `Out` becomes `structuredContent`.
  - `ToolAnnotations{Title string; ReadOnlyHint bool; DestructiveHint *bool; IdempotentHint bool; OpenWorldHint *bool}`
    (`protocol.go:~1960-1990`). Since v1.7 the two bools are always serialized.
  - `mcp.NewStreamableHTTPHandler(getServer func(*http.Request) *Server, opts *StreamableHTTPOptions)`
    (`streamable.go:231`). Options: `Stateless`, `JSONResponse`, `Logger`, `EventStore`, `SessionTimeout`,
    `DisableLocalhostProtection`, `CrossOriginProtection` (`streamable.go:135-185`).
    **2026-07-28 requests are accepted only when `Stateless: true`**; stateful servers negotiate down to 2025-11-25.
  - **Gotcha:** default DNS-rebinding protection 403s a request that arrives from 127.0.0.1/::1 with a non-localhost
    `Host` header. That is exactly a reverse proxy on the same host. Set `DisableLocalhostProtection: true`. That is
    safe here because every `/mcp` call needs a bearer token, which a rebinding browser cannot send.
  - `s.Run(ctx, &mcp.StdioTransport{})` for stdio (`server.go:1354`).
  - `auth.RequireBearerToken(verifier, opts)` middleware (`auth/auth.go:97`). Not needed: remora's own
    `auth.Service.Authenticate` already does this.
- **`mark3labs/mcp-go`**: community, implements 2025-11-25 (and back to 2024-11-05), says it is "under active
  development", no 2026-07-28. https://github.com/mark3labs/mcp-go . No reason to pick it over the official SDK.
- **Spec:** current revision **2026-07-28**. It is stateless by default, removes `Mcp-Session-Id` (SEP-2567) and the
  GET stream, adds `Mcp-Method`/`Mcp-Name` headers, and replaces `initialize` with `server/discover` (deprecated with
  notice). These points come from secondary sources and the go-sdk release notes
  (https://github.com/modelcontextprotocol/go-sdk/releases); verify against modelcontextprotocol.io before relying on
  a detail.
- **Claude Code** (https://code.claude.com/docs/en/mcp):
  `claude mcp add --transport http remora https://HOST/mcp --header "Authorization: Bearer $REMORA_TOKEN"`;
  stdio: `claude mcp add --transport stdio --env REMORA_URL=… --env REMORA_TOKEN=… remora -- remora mcp`.
  `.mcp.json` expands `${VAR}` in `url`/`headers`. Default output cap 25k tokens (`MAX_MCP_OUTPUT_TOKENS`); results over
  50k chars spill to a file. Tool search is on by default. Permission rules match `mcp__remora__<tool>`, so a split
  read/write surface lets a user allow `mcp__remora__remora_inspect` and keep writes on ask. Unverified: whether Claude
  Code auto-trusts `readOnlyHint`. Do not rely on it.

## 4. Recommended minimal design for remora

### Transport and auth

1. **Streamable HTTP at `/mcp`** on the same listener: `mux.Handle("/mcp", …)` in `serve.go`, next to `/api/`.
   `StreamableHTTPOptions{Stateless: true, JSONResponse: true, DisableLocalhostProtection: true}`. There are no sessions
   to store, no GET stream, and the 2026-07-28 and older clients both work.
2. **Auth = the existing API token.** Wrap the handler in `auth.Service.Middleware(nil)`. Accept the **bearer token
   only**, not the session cookie: a browser has no business on `/mcp`, and dropping the cookie removes CSRF from the
   picture. No new token type, no scopes, no OAuth. The token is created in Settings → API tokens, as for the CLI.
3. **`remora mcp` (stdio)**, a fourth CLI command next to apply/export/import. It reuses `connFlags`/`newClient`
   (`REMORA_URL`, `REMORA_TOKEN`) and talks to a running remora over HTTP. It is cheap because it is the same tool code
   over a different `gen.Client`.

### In-process or HTTP? Through the generated client, both ways

Tools call **`gen.ClientWithResponses`**, never the handlers or store directly.
- Under `/mcp`, the client's `http.Client.Transport` is a RoundTripper that calls `mgmt.Handler().ServeHTTP` in
  process, through `httptest.NewRecorder` or a pipe, and copies the **caller's `Authorization` header** onto every call.
  The API middleware re-authenticates it with one sha256 lookup. It has no network hop and no second auth path, and
  validation, error shape, `no-store` and reconcile all stay exactly the API's. This is OmniRoute's `omniRouteFetch`
  idea without the socket and without the server-credential fallback bug.
- Under stdio, the same tools get a real network `gen.Client` from `newClient`.
- Calling `Server` methods directly would be marginally faster but would bypass the auth middleware and duplicate request
  validation. Not worth it at management-API volumes.

### Tools (12)

Read tools: `readOnlyHint: true`, `idempotentHint: true`. Write tools: `readOnlyHint: false` and an explicit
`destructiveHint`.

| # | Tool | R/W | Inputs | Covers (operationIds) |
|---|---|---|---|---|

| 2 | `remora_inspect` | R | `kind`: provider\|account\|alias\|key\|api_token\|cooling\|login; `id?` (name or id; omitted = list); `limit?`, `offset?` | `list*`/`get*` for each kind; alias with `id` returns `getAliasChain` (members with cooling marks); key with `id` adds `getKeyUsage`; login = `getAccountLogin`. So there are **11 real tools**. Row 12 is listed only to show the decision.

Why apply and not per-entity write tools: `prune=false` on a partial document is a precise upsert (`plan.go:46-51`).
So "add a fallback member to alias `fast`" is: `remora_inspect alias fast` (or export), write a 6-line YAML with that
alias, plan, apply. One write path, already validated against `remora.schema.json`, already tested, already diffed.
Three write tools (`provider_write`, `alias_write`, `key_write`) and their 9 operations disappear.
**Must verify before relying on it:** that a partial document whose alias members reference providers *absent from
the document* plans cleanly against the store (the plan comment covers secrets, not member references). If it does
not, the agent includes the referenced providers with their `env:` refs unset, which keeps the stored secrets.

### Applying a whole config safely

1. `remora_config_export` → the agent edits the YAML (or writes a partial one).
2. `remora_config_plan {document, secrets, prune}` → `changes[]` + `plan_hash = sha256(canonical JSON of changes)`.
   The agent shows the changes to the user.
3. `remora_config_apply {…same…, plan_hash}`: the tool **re-plans first** and refuses with the fresh plan if the hash
   differs (the store moved, or the agent changed the document). That is about 10 lines in the MCP layer, no API
   change, and it closes the plan/apply race the CLI has too.
4. `prune` defaults to **false** in MCP (the CLI defaults to true). A whole-config replace must say `prune: true`. Then
   the plan's `delete` rows are what the user is confirming, and `destructiveHint` makes clients ask.
5. Secrets: the agent passes real provider keys in `secrets` only for new or rotated keys. An absent NAME keeps the
   stored secret, so a round-trip export→apply never needs secrets.

Confirmation is the client's job (annotations + Claude Code permission rules on `mcp__remora__*`). Do not build
elicitation round-trips. The plan_hash guard is the server-side safety.

### Switches (cheap, worth it)

- `REMORA_MCP=off` disables the `/mcp` mount (default on? Recommend **on**, since it is behind the same token as `/api`).
- `remora mcp --read-only` and `REMORA_MCP_READ_ONLY=true` register only tools 1-8, as GitHub's `--read-only` does.

### Deliberately excluded from the MCP surface

- `changePassword`, `createApiToken`, `deleteApiToken`: an agent minting its own credentials or locking the admin out is
  pure blast radius. A human does these in Settings.
- `login`/`logout`/`getSession`: meaningless over bearer auth.
- `streamLogs` (WebSocket): agents poll `remora_logs` with `from`. A live stream does not fit request/response tools.

### Recommend NOT building

- **Resources** (`remora://config`, etc.): clients surface them inconsistently, and `remora_config_export` and
  `remora_inspect` already return the same data where agents actually look.
- **Prompts**: canned workflows belong in a Claude Code skill or the README, not the protocol.
- **Sampling**: remora never needs to call the client's model.
- **Elicitation** for confirmations: client permission rules plus `destructiveHint` plus plan_hash already cover it;
  elicitation needs a stateful/MRTR round trip and client support varies.
- **Tasks / long-running ops**: every management call returns in well under the 2-minute client timeout
  (`cmd/remora/client.go:29`).
- **Stateful sessions, SSE GET stream, EventStore/resumability**: stateless JSON responses suffice and align with
  2026-07-28.
- **OAuth 2.1 / protected-resource metadata**: a self-hosted single-admin box. The existing API token is the
  credential, as for the CLI.
- **Per-tool scopes / roles**: remora tokens have no scopes today. Add a read-only switch, not an RBAC system.
- **OpenAPI-driven generated tools or Cloudflare-style code mode**: 45 operations do not need it, and generated
  per-endpoint tools are the bloat OmniRoute had to patch with tool search and description compression.
- **A `route_request`/chat tool**: the agent already has `/v1`. This is noise copied from OmniRoute.
- **MCP tool audit table**: every call already lands in the API's request path. Add logging if asked.
- **Tool search / description compression**: only needed at 100+ tools.

  *mcp.Server` plus an in-process RoundTripper. Wire it in `serve.go` and a new `cmd/remora/mcp.go`.
