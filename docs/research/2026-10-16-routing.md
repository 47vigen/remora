## 1. OmniRoute

Two separate selection layers. Both live in process and memory, with no engine underneath.

### 1a. Combos (OmniRoute's aliases)

The strategy list is `src/shared/constants/routingStrategies.ts:1-22`: 20 public values plus the internal
`quota-share`. Each strategy only **reorders the target list** before the attempt loop
(`open-sse/services/combo/applyStrategyOrdering.ts:348-358`). The attempt loop then walks the ordered list.
Fallback is "the next element", and cooling targets are skipped there
(`comboAttemptLoop.ts:103-112,169-177`). Per-strategy traits are data in `strategyRegistry.ts:117-181`.

| strategy | ordering (applyStrategyOrdering.ts) | signal | fallback after the first pick |
|---|---|---|---|
| `priority` | none: declared order (`strategyRegistry.ts:118-126`) | none | declared order. Extras: pre-screen of targets, `fallbackOnlyOnQuotaExhaustion` targets, stickiness may not reorder the declared order |
| `fill-first` | **none**: "preserving priority order" (`:276-282`) | none | declared order. **Same order as `priority`**, without priority's extras |
| `round-robin` | own dispatcher `roundRobinCombo.ts`: atomic counter `counter % n` (`:137,358-364`), sticky-N start index, per-target semaphore (default concurrency 3, `:178`) | per-combo counter and in-flight semaphore | rotates from the start index (`:487`). Queues or falls over on semaphore timeout |
| `random` | Fisher-Yates over the **whole** list (`:271-275`) | none | the shuffled order, so failover is random too |
| `p2c` | `orderTargetsByPowerOfTwoChoices` (`targetSorters.ts:142-156`) | `successRate/100 + 1/log10(avgLatencyMs+10)`, minus 0.25 when the provider breaker is HALF_OPEN and −∞ when it is OPEN (`:126-140`). Metrics are per **model**, cumulative and in memory (`comboMetrics.ts`) | the winner first, then the rest in declared order |
| `least-used` | `sortTargetsByUsage` (`targetSorters.ts:107-124`) | **cumulative** request count per `executionKey` (model+account) since process start or a metrics reset | ascending by count |

Other notes:
- p2c does **not** use in-flight, quota or errors directly, only success rate, latency and the breaker. Least-used is
  lifetime count, not windowed. A member that rejoins after a long cooldown therefore takes every request until its
  count catches up. This is a known weakness: #7015 fixed only the keying.
- Session stickiness (`sessionStickiness.ts`, 15-minute TTL, `:69`) runs **after** strategy ordering
  (`targetResolution.ts:481` then `:542`). For `priority` it may not break the declared order
  (`stickinessRespectsDeclaredOrder`). For p2c, random, least-used and round-robin it moves the bound target to the
  front. Prompt-cache affinity can be re-pinned behind the strategy's first pick
  (`protectsFirstTargetFromAffinity`).
- Near-duplicates: `fill-first` ≡ `priority` (same order, fewer features). `strict-random` (a deck) is a low-variance
  `random`, close to `round-robin`. `least-used` matches `round-robin` in steady state when all targets are equal.

### 1b. Accounts (connections of one provider)

Lives in `src/sse/services/auth.ts`. Strategy = `settings.providerStrategies[provider].fallbackStrategy ||
settings.fallbackStrategy || "fill-first"` (`:1871-1876`), so it is **per provider, with a global default**. The
candidates are already filtered for rate-limited and unavailable connections (`rateLimitedUntil`,
`isAccountUnavailable`) and sorted by `priority` ascending (`:1861-1869`). Session affinity is checked **first** and
wins over every strategy (`:1883-1915`). Account fallback = call again with the failed connection excluded.

| strategy | code | signal |
|---|---|---|
| `priority` | **no branch**: falls into the default (`:2074`) = `fill-first` | priority field |
| `fill-first` | `orderedConnections[0]` (`:2074-2076`) | priority field |
| `round-robin` | sticky-N (default 3) on the most recently used, then LRU by `lastUsedAt` with lower `backoffLevel` first. In fallback mode, always LRU (`:1916-2001`) | `lastUsedAt`, `consecutiveUseCount`, `backoffLevel` (persisted) |
| `p2c` | two random candidates; the lower `getP2CConnectionScore` wins (`:2002-2020`, score at `:557-604`) | the richest signal: quota exhausted (+200) or blocked (+80), quota-headroom penalty, recent-error penalty by status, `backoffLevel*8`, consecutive use, recency (15 s/60 s/5 min), priority |
| `random` | uniform (`:2021-2025`) | none |
| `least-used` | oldest `lastUsedAt`, with lower backoff first (`:2026-2053`) | `lastUsedAt`, so this is **LRU**, which is round-robin without stickiness |
| `cost-optimized` | sort by priority (`:2054-2060`) | priority, so ≡ fill-first |

`open-sse/services/accountSelector.ts` (a P2C and strategy switch) has **no callers**. It is dead code; ignore it.

Account-level near-duplicates: `priority` ≡ `fill-first` ≡ `cost-optimized`. `least-used` ≈ `round-robin` with
sticky limit 1. Only `p2c` and `random` are distinct. 9router, which OmniRoute forked from, has only `fill-first`
and sticky `round-robin` for accounts (`auth.js:146-198`). For combos it has `fallback`, `round-robin` and `fusion`,
per combo or global (`chat.js:107-135`).

## 2. Other prior art

- **LiteLLM Router** (https://docs.litellm.ai/docs/routing):
  - `simple-shuffle` (default): random, weighted by `weight`, `rpm` or `tpm`.
  - `least-busy`: the fewest **in-flight** requests per deployment, counted by pre-call and success/failure callbacks.
  - `usage-based-routing-v2`: the lowest TPM or RPM **in the current minute** (Redis), skipping deployments over their limit.
  - `latency-based-routing`: the lowest rolling average latency, with `lowest_latency_buffer` to spread near-ties and TTFT for streams.
  - `cost-based-routing`: the cheapest per token.
  - Priority comes from `order` in `litellm_params`. Fallback runs over `fallbacks` model groups. Cooldown is
    `allowed_fails` within a minute, then `cooldown_time`.
- **Envoy** `LEAST_REQUEST` (https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers):
  P2C by default (`choice_count: 2`). It picks the host with fewer **active requests**, and when weights differ it
  scales by weight / (active+1)^bias. `RANDOM` and `ROUND_ROBIN` are separate policies.
- **Finagle** (https://twitter.github.io/finagle/guide/Clients.html#load-balancing): "P2C least-loaded" = outstanding
  requests. "P2C + Peak EWMA" = peak-sensitive latency × (outstanding+1). This is the canonical p2c: two random
  choices, compared on a **local, exact load signal**.
- **Portkey** (https://portkey.ai/docs/product/ai-gateway/load-balancing): `strategy.mode: loadbalance` = weighted
  random over targets. `mode: fallback` with `on_status_codes`. Targets nest, so a loadbalance target may itself be
  a fallback group.
- **CLIProxyAPI v8.0.31** (the engine remora runs):
  - Strategies: `round-robin` (default), `weighted-round-robin`, `fill-first`. Nothing else
    (`internal/config/config_types.go:389-392`, `sdk/cliproxy/service_config.go:78-82,103-118`, management
    `config_basic.go:312-324`).
  - **Global only**: one `routing.strategy`. Rotation state is keyed `provider:model` (`selector.go:622`).
  - **Per-auth `priority`**: integer, read from auth attributes (`selector.go:364-377`). The selector takes only the
    **highest-numbered available tier** (`collectAvailableByPriority`/`highestPriorityAuths`, `selector.go:469-575`)
    and runs the strategy inside that tier. Cooling, disabled and expired auths drop out before the tier is picked
    (`isAuthBlockedForModel`, `selector.go:822+`).
  - Round-robin rotates by ID ring, resuming after the last pick (`selector.go:614-653`).
  - Fill-first = `available[0]` of the top tier (`:812-821`).
  - Per-auth `weight` exists for WRR.
  - Priority and weight are settable on a live credential through the management `PATCH .../fields` endpoint that
    remora already uses for `prefix` (`internal/api/handlers/management/auth_files_fields.go:349-365,621,696-724`).
  - Session affinity (perf-upstream turns it on) wraps the strategy. An established binding **outranks priority**
    (config.example.yaml comments at `:159-161`).
  - **No HTTP auth pin.** `pinned_auth_id` is set only from the in-process context (`sdk/api/handlers/handlers.go:276-277`
    ← `WithPinnedAuthID`, called only by `ModelExecutionRequest.AuthID` for plugins and internal callers
    (`model_execution.go:117,154`), Codex live sessions, and videos).
  - A **scheduler plugin** API exists (`sdk/pluginapi/types.go:469-545`, `internal/pluginhost/scheduler.go`). It
    returns an AuthID or delegates to a builtin. It is loaded as a native Go plugin, and remora runs with
    `plugins.enabled: false` (`internal/supervise/cliproxyapi.go`).
- **Bifrost (fork of transports/v2.3.0)**:
  - A routing rule has weighted `targets`, picked by weighted random (`plugins/routing/rules/engine.go:276,359-398`),
    and **one** fallback chain per rule, shared by every target (`:302`). This is why remora's `Spread` cannot
    exclude the picked member from its fallbacks (`internal/reconcile/desired.go:294-297`).
  - The rule's CEL sees `model`, `provider`, **all request headers** (lowercased, `transports/bifrost-http/lib/ctx.go:827-832`,
    `engine.go:481-490`), query params, the VK scope and budget/rate usage.
  - The first matching rule in priority order wins (`engine.go:215-311`).
  - Per-key `weight` with a `WeightedRandom` key selector (`core/bifrost.go:326-327`, `core/schemas/account.go:143`).
  - VK provider-config load balancing is weighted random (`plugins/governance/main.go:481+`).
  - No adaptive or latency balancing in the open-source build.
  - **Body `fallbacks`** (`["provider/model", ...]`) are honored (`transports/bifrost-http/handlers/inference.go:80,414`).
    A matching rule with non-empty fallbacks **replaces** them (`plugins/routing/main.go:544-560`).

## 3. Where each strategy can live without editing `engines/`

### Alias level (Bifrost)

**(a) The proxy rewrites `model` to the picked target and puts `fallbacks` in the body.** Bifrost honors this, but
only when no alias rule matches: remora's rule CEL matches the alias's engine model, so a rewritten model skips it.
- Kept: the VK allowlist. remora's VKs are `allow_all_providers` and remora enforces the allowlist itself.
- Lost: the routing-rule name in the engine's routing log, the "the engine owns the chain" property, and the
  zero-copy body path. The proxy has to re-serialise the body, which goes against the perf work.
- Verdict: works, but costs more and changes more than (b′).

**(b) Compile into rule config only.** This is what exists today. Weighted-random `Spread` is the only spreading
primitive. Without per-request input nothing stateful (`round-robin`, `p2c`, `least-used`) is possible, and the
fallbacks repeat the picked member.

**(b′) Recommended: header-selected rules.** The compiled rules stay the engine's job, and the proxy only chooses
which rule fires.
- For an alias with strategy ≠ priority and live members m1..mn, compile **one rule per live member**:
  - `RuleCEL(alias) && headers["x-remora-first"] == "<member ref>"`
  - target mi
  - fallbacks = the other live members in rotated order (mi+1..mn, m1..mi−1)
- Also compile the existing header-less rule (declared order) at a lower priority, as the safe default.
- The proxy sets `X-Remora-First` per request from the strategy. It deletes any client-sent value next to
  `setUpstreamHeaders`.
- No body rewrite. Engine logs and rule names stay intact. The picked member is never repeated in its own chain, so
  the `maxFallbacks` cap and `Spread` can be deleted.
- A cooled member's rule disappears on recompile. A stale header then matches nothing and falls through to the
  default rule.
- Cost: n rules per spreading alias, which means more CEL evaluations per request (cheap, but measure with
  `internal/proxy/bench_test.go`). Rule priorities must stay distinct, which the reconciler already guarantees.

### Account level (CLIProxyAPI)

- No per-request steering: there is no auth-pin header. Per-account prefixes would let the model name pin an account,
  but they break the native pool, its cooldown and retry, and session affinity.
- What can be set per pool: the per-credential `priority`, through the existing management PATCH.
- What cannot: the strategy itself, which is one global setting.
- Smallest honest mapping: keep global `routing.strategy: round-robin` and express the pool's strategy through
  priorities:
  - `round-robin`: every account of the pool at priority 0. One tier, so native round-robin. Unchanged from today.
  - `fill-first`: priorities by list order (first = highest, distinct). Every tier holds one account, so the top
    available account always wins. When it cools or is disabled the engine drops to the next tier by itself.
  - `priority`: user-given integer tiers. Equal numbers rotate round-robin inside the tier, and the top available
    tier wins. `fill-first` is the special case "all tiers distinct, in list order".
- `p2c`, `least-used`, `random` are **not honestly implementable** here. The engine exposes no per-account in-flight
  or usage signal to selection, and remora cannot see or choose the account. The only routes are an engine patch or
  a native scheduler plugin (rejected below).

## 4. Recommended minimal design

### Signals remora has, and has not

- Has: cooling (`internal/cooling`), fed by the 1 s log tail (`internal/engine/bifrost/tail.go:12`) every 5 s
  (`cooling/source.go:16`), in memory. It also has `x-remora-served-by` on every response
  (`internal/proxy/servedby.go`) and the compiled live chain per alias.
- Has not: **in-flight counts**. Nothing in `internal/proxy` counts requests in flight today, so they must be added.
  This is simple once the proxy picks the member: increment when the request is sent, decrement when the response
  body closes (stream end included). If `served-by` names another member, move the count to it when the response
  headers arrive.

### Alias level

State is in memory, like cooling, and resets on restart. "Live members" = the compiled chain after the cooling
filter. A cooling member is never picked, because it has no rule. Fallback after the first pick = the rule's chain:
the other live members in rotated order, so failover load spreads as well (the lesson of OmniRoute #3959).

| strategy | pick of the first member | state | scope |
|---|---|---|---|
| `priority` (default; today's "no strategy") | declared order, no header | none | n/a |
| `fill-first` | **synonym of `priority`**. At alias level "stay on the first until it fails" is exactly priority plus cooling. Accept it on input, store it as priority, and document that it exists for parity | none | n/a |
| `round-robin` | atomic counter mod len(live) | one counter per alias | per alias |
| `random` | uniform over live (today's behavior, moved from `Spread` to header rules) | none | n/a |
| `p2c` | two distinct random live members; the one with fewer **in-flight** requests wins; ties go to declared order. This is Envoy and Finagle p2c | in-flight counter per target | **global per target**, because aliases share members |
| `least-used` | the live member with the fewest requests **started in the last 60 s** (sliding window); ties go to declared order. This is LiteLLM usage-based v2 on RPM, not OmniRoute's lifetime count | request timestamps per target in a 60 s ring | global per target |

- The existing stored value `round-robin` changes meaning from random to a true rotation. Strictly better, but say so
  in CHANGELOG.
- Nested aliases flatten as today. The strategy of the outer alias applies to the flat chain.

**Session affinity:** spreading per request breaks prompt caching for a conversation.
- For the spreading strategies (`round-robin`, `random`, `p2c`, `least-used`), reuse perf-upstream's `affinityKey`.
- The first turn picks by the strategy and records key→member (TTL 1 h, bounded map). Later turns reuse the member
  while it is live, and rebind once it cools. That matches CLIProxyAPI's semantics at account level.
- `priority` needs no affinity.

### Account level (per subscription provider)

- `priority` (explicit tiers), `fill-first` (tiers in list order) and `round-robin` (one tier, the default) all
  compile to per-credential `priority` through `PATCH /credentials/fields` in `internal/accounts` reconcile.
- The global `routing.strategy` stays `round-robin`. Cooldown, retry and affinity stay the engine's.
- `p2c`, `least-used` and `random`: **reject at validation** with "not available for accounts; round-robin is the
  closest". Over a cooling-aware ring, round-robin gives the even spread that least-used and random approximate. p2c
  has no signal at this level.

### Build order (smallest first)

1. Account priorities. Config plus reconcile only, with no request-path code.
2. Header-selected rules in reconcile, with `random` and `round-robin` in the proxy. Delete `Spread`.
3. In-flight and windowed counters, with `p2c` and `least-used`.
4. Alias affinity binding.

### Recommend NOT building

- **Account-level p2c, least-used, random**: no per-account signal or steering without an engine patch.
- **CLIProxyAPI scheduler plugin**: a native Go plugin tied to the exact engine build and toolchain, and it would
  re-enable the plugin host.
- **Per-account prefixes to pin accounts**: would replace the engine's pool, cooldown, retry and affinity with
  remora code.
- **Body `fallbacks` rewrite (option a)**: re-serialises every body, and header rules do the same job.
- **Weighted / `weighted-round-robin`**: not asked for, and the engine primitives exist if it is wanted later.
- **Latency-based or OmniRoute-style p2c scoring** (success rate + latency): noisy across model sizes, and 1 s-polled
  logs are stale; in-flight is exact and local.
- **Lifetime-count least-used**: floods a member that rejoins after cooling.
- **OmniRoute's cost-optimized, reset-aware, headroom, quota-weighted, auto, lkgp, fusion, strict-random,
  context-relay**: they need cost or quota data remora lacks, or `round-robin` already covers them.
- **Sticky-N round-robin** (OmniRoute and 9router `stickyRoundRobinLimit`): the affinity key solves the real need,
  which is the prompt cache.
- **Persisting counters across restarts**: cooling is in memory too, and counters rebuild in seconds.

## Open risks

- Rule count grows to aliases × members for spreading aliases. Benchmark CEL evaluation per request before shipping.
- Assumed and not verified in e2e: Bifrost does not forward the arbitrary `X-Remora-First` header upstream. It
  forwards only `x-bf-eh-*`. Add an e2e assertion against the fake upstream.
- The main checkout's `engines/cliproxyapi` working tree is at v8.0.30 while the pin is v8.0.31. Run
  `git submodule update` before anyone reads engine code from the main checkout.
