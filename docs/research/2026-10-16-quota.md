# Subscription account quota monitoring: research

Date: 2026-10-16. Scope: the "Provider Quota" feature for remora (per-account quota of subscription OAuth accounts,
one page for all of them). Everything below carries file:line or URL evidence. Paths under `engines/cliproxyapi` are
relative to `engines/cliproxyapi`. OmniRoute paths are relative to a sparse clone at
commit `ddf2759e` (2026-10-16).

Note on the engine pin: `engines/versions.env` says `CLIPROXYAPI_VERSION=v8.0.31`, but the submodule checkout is at
tag `v8.0.30` (`git describe` / `git tag --points-at HEAD`). The v8.0.30→v8.0.31 diff
(`gh api repos/router-for-me/CLIProxyAPI/compare/v8.0.30...v8.0.31`) touches none of the files cited here
(`api_tools.go`, `plugin_quota.go`, `auth_files.go`, `quota_signals.go`, `server_management_v8.go`), so every engine
finding holds for v8.0.31. The checkout mismatch itself is worth fixing separately.

## 1. The answer to the most important question

**Yes: remora can get exact per-account quota for every provider that matters without patching the engine.**

The engine exposes `POST /v8/management/requests/api-call` (`internal/api/server_management_v8.go:30`, same handler
as v0 `POST /v0/management/api-call`, `internal/api/server_management.go:73`). It sends an arbitrary HTTP request
upstream **as a given credential**:

- Request: `{auth_index, method, url, header, data, proxy_url?}`. The magic string `$TOKEN$` in a header or body is
  replaced by that credential's current access token (`internal/api/handlers/management/api_tools.go:64-79`, handler
  at `:104`).
- Token resolution is provider-aware: Antigravity refreshes its OAuth access token first, xAI refreshes when due,
  Meta has its own path, everything else uses `metadata.access_token`
  (`api_tools.go:273-294`).
- The request goes out through the credential's own proxy, else the global proxy (`api_tools.go:81-85`,
  transport at `:213`), so quota probes leave from the same egress as inference. 60 s timeout (`api_tools.go:24`).
- Response: `{status_code, header, body}` with HTTP 200 whenever the call itself happened (`api_tools.go:87-90`,
  `:232-237`).

remora already talks to `/v8/management` (`internal/engine/cliproxyapi/client.go:20`) with the management secret, so
this is one new client method. The engine's own web console (CLIProxyAPI Management Center) builds its whole quota
page this way: every request header set it uses carries `Authorization: Bearer $TOKEN$`
(`router-for-me/Cli-Proxy-API-Management-Center/src/utils/quota/constants.ts:94-97,107,135,145,161`), and its
Antigravity fetcher calls `apiCallApi.request({url, ...})` (`src/features/quota/providers/antigravity/data.ts:144-149`).
So this is the sanctioned path, not a trick.

The account identifiers remora needs for the upstream calls are already in `GET /v8/management/credentials`, which
remora calls today (`internal/engine/cliproxyapi/client.go:74`):

- `auth_index` (`auth_files.go:663-664` area, entry built at `:658-680`)
- `project_id` for Antigravity (`auth_files.go:704`)
- `id_token` claims for Codex, including `chatgpt_account_id` and `plan_type` (`auth_files.go:744`, claim extraction
  `auth_files.go:~928-931`)

### What the engine already holds, for free

| data | where | providers | cost |
|---|---|---|---|
| Passive quota signals: the quota headers of the last upstream response, with `observed_at` | `GET /credentials` → `quota.signals`, `model_quotas` (`auth_files.go:682-685`, payload `:800-817`) | **codex, claude, devin only** (`sdk/cliproxy/auth/quota_signals.go:17-24`) | zero upstream calls |
| Per-credential and per-model cooldowns with reason, `retry_at`, `remaining_seconds`, HTTP status | `GET /credentials` → `cooldowns` (`auth_files.go:145-163`) | all | zero |
| `next_retry_after`, `status`, `status_message`, `unavailable`, `disabled`, `success`/`failed`, `recent_requests` | `GET /credentials` (`auth_files.go:658-681,725`) | all | zero |
| Cooldown reset | `POST /v8/management/routing/cooldown/reset` (`server_management_v8.go:31`) | all | zero |

Codex signals captured passively: `x-codex-plan-type`, `x-codex-active-limit`, `x-codex-credits-*`,
`x-codex-primary-*` / `x-codex-secondary-*` (`-used-percent`, `-window-minutes`, `-reset-after-seconds`,
`-reset-at`), `x-codex-limit-reached`, additional per-model limits, and `retry-after`
(`quota_signals.go:146-213`). Claude: `anthropic-ratelimit-unified-*` and `retry-after` (`quota_signals.go:176-180`).
The websocket path folds the `codex.rate_limits` event into the same headers
(`internal/runtime/executor/helps/codex_quota.go:16-60`). remora today **drops all of these** and shows only
cooldowns as quota (`internal/api/adapters.go:590-621`: "The engine's other quota signals are opaque and not shown").

Antigravity emits **no** passive signals (not in `ProviderSupportsQuotaObservation`), so its quota must be polled.

### What does not work without patching or plugins

- `POST /v0/management/quota/fetch` (`server_management.go:85`, `plugin_quota.go:60-133`) only answers when a
  quota **plugin** is loaded (`plugin_quota.go:88-111`; `GET /quota/providers` lists them and is empty without
  plugins, `plugin_quota.go:44-57`, `internal/pluginhost/quota_provider.go:64`) or when the credential JSON carries a
  declarative `quota_probe` (`plugin_quota.go:114-129`, executor `:383`, mapper `:634`). Otherwise 501. It is v0-only
  (`auth_files.go:693`: "Declarative quota_probe is only executed by the v0 quota/fetch route"; no route in
  `server_management_v8.go`).
  - Plugins are cgo Go plugins installed from a store (`server_management_v8.go:52-58`): third-party code inside
    the engine. Reject.
  - `quota_probe` could be injected into the credential file at import, but its mapper is a flat gjson projection
    (`plugin_quota.go:634-822`). It cannot express Antigravity's family×window shape or Codex's
    primary/secondary/additional windows cleanly, and it ties remora to a v0 route. api-call plus Go parsing in remora
    is simpler and testable. Reject.
- The engine fetches Antigravity `fetchAvailableModels` itself, but only for capability hints (model IDs), cached
  per `registry.ModelsRefreshInterval`. It keeps no quota fields from that call
  (`sdk/cliproxy/antigravity_models.go:29-32,446-497,557`). Nothing to reuse.

## 2. Upstream endpoints per provider (what OmniRoute and the engine console call)

All are undocumented, private endpoints of the vendors' own clients. They can change without notice, so every parser
must accept missing fields and show "unknown", never 0 %.

### Antigravity (Google Cloud Code), the owner's main pool

| call | purpose | evidence |
|---|---|---|
| `POST {base}/v1internal:retrieveUserQuotaSummary` body `{"project": <project_id>}` | **Primary.** Quota per model *family* (Gemini; Claude & GPT), each with independent **5-hour (session)** and **weekly** windows; `remaining.remainingFraction` + `remaining.resetTime` (or flat `remainingFraction`/`resetTime`); `disabled` buckets skipped | OmniRoute `open-sse/services/usage/antigravityWeeklyQuota.ts:1-8,82-86,129-180`; engine console uses only this call for quota: `cpamc constants.ts:68-72`, `ag-data.ts:129-172` |
| `POST {base}/v1internal:retrieveUserQuota` body `{"project": ...}` | Per-model buckets `{modelId, remainingFraction, resetTime}`, the real consumption signal for per-model buckets | OmniRoute `usage/antigravity.ts:257-303,558-563,637-644` |
| `POST {base}/v1internal:fetchAvailableModels` body `{"project": ...}` | Model catalog with `quotaInfo.remainingFraction/resetTime`. OmniRoute itself warns it is "catalog/eligibility data and may keep reporting full buckets after real usage" | `usage/antigravity.ts:192-255,558-563,654-690` |
| `POST https://cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` | Plan tier (free / pro / ultra) and the companion project | `usage/antigravity.ts:61,790-836`; console `constants.ts:74-75` |

Bases: `https://daily-cloudcode-pa.googleapis.com`, then `https://cloudcode-pa.googleapis.com`
(OmniRoute `open-sse/config/antigravityUpstream.ts` runtime bases; the engine defaults to the daily base,
`antigravity_models.go:29,516-535`). Headers: `Authorization: Bearer $TOKEN$`, `Content-Type: application/json`, and the
engine's own Antigravity UA `antigravity/hub/<version> <platform>` (`internal/misc/antigravity_version.go:116-117`).
The console warns that "Cloud Code rejects newer models for clients below 2.23.0" (`constants.ts:77-79`). remora
should read the UA the engine uses, or mirror it, and never invent its own. Semantics: no `resetTime` together with
fraction 1.0 means unlimited (`antigravityWeeklyQuota.ts:162-163`, `antigravity.ts:687-689`). A missing fraction is
"unknown", not 0 % (`antigravity.ts:677-686`).

### Codex (ChatGPT subscription)

- `GET https://chatgpt.com/backend-api/wham/usage`, headers `Authorization: Bearer $TOKEN$`,
  `chatgpt-account-id: <chatgpt_account_id>`, and a Codex client UA (OmniRoute `open-sse/services/usage/codex.ts:17-19,46-59`;
  console `constants.ts:127,134-138`; CodexBar `docs/codex.md:45`).
- Response: `plan_type`, `rate_limit.{limit_reached, primary_window, secondary_window}` each with `used_percent`,
  `limit_window_seconds`, `reset_after_seconds`/`reset_at`; plus `code_review_rate_limit`, `additional_rate_limits`
  (per-model, e.g. Spark), `rate_limit_reset_credits`, `rate_limit_reached_type`
  (OmniRoute `open-sse/services/codexUsageQuotas.ts:78-160,241-259`). Label windows by `limit_window_seconds`, not by
  primary/secondary (`codexUsageQuotas.ts:135-141`).
- **Passive alternative, free:** the engine already captures the same numbers as `x-codex-*` headers on every
  inference response (section 1). For an account that served traffic recently, the passive snapshot is as good as a
  poll. Poll only accounts whose snapshot is stale or absent.

### Claude (Claude Code OAuth)

- `GET https://api.anthropic.com/api/oauth/usage`, headers `Authorization: Bearer $TOKEN$`,
  `anthropic-beta: oauth-2025-04-20`, a claude-code UA (OmniRoute `usage/claude.ts:40-45,194-205`; console
  `constants.ts:103-110`).
- Response windows: `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_oauth_apps`, … each
  `{utilization (percent used), resets_at}`; `extra_usage` (`usage/claudeQuota.ts:39-65,181-206`; console window list
  `constants.ts:112-124`).
- The endpoint rate-limits its own callers: OmniRoute caches a success for 65 s and keeps showing the last known
  value on 429 (`usage/claude.ts:47-55`).
- Passive: `anthropic-ratelimit-unified-*` headers are captured by the engine (section 1).

### Kimi (Kimi Coding OAuth)

- `GET https://api.kimi.com/coding/v1/usages` (console also tries `api.kimi.ai`), `Authorization: Bearer $TOKEN$`
  (OmniRoute `usage/kimi.ts:27-29,240`; console `constants.ts:141-147`).
- Response: `usage` (the 7-day pool: `limit`, `used`, `remaining`, `resetTime`) and `limits[]`, each an independent
  rolling window with `detail` (`usage/kimi.ts:132-149,271-290`).

### Grok / xAI (OAuth)

- `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits`, `Authorization: Bearer $TOKEN$` plus
  `x-xai-token-auth: xai-grok-cli`, `x-grok-client-version`, a grok-cli UA (OmniRoute
  `open-sse/services/xaiOauthQuotaFetcher.ts:1-20`, `grokQuotaFetcher.ts:31,79,327`; console `constants.ts:149-167`).
- Response: `creditUsagePercent` (0-100, used) and `currentPeriod.end` (reset). One weekly pool.
- The engine deliberately excludes Grok from passive observation (`quota_signals.go:183-188`).

### Qwen, iFlow, others

- OmniRoute has no usage fetcher for Qwen OAuth or iFlow; it covers only the paid `qwen-cloud-token-plan` and Bailian
  API-key plans (`open-sse/services/usage/supportedProviders.ts:20-91`). The engine console has no Qwen or iFlow
  quota provider either (`src/features/quota/providers/`: antigravity, claude, codex, devin, kimi, meta, plugin, xai).
  **No known endpoint. Show cooldowns only.**

## 3. OmniRoute: what its Provider Quota page does

The page lives at `src/app/(dashboard)/dashboard/quota/page.tsx` and renders `usage/components/ProviderLimits`.

- **Rows:** one card per connection, grouped by provider in a fixed order (`ProviderLimits/constants.ts:1-46`). Each
  card shows the plan label and mini-bars per quota window or model (`QuotaCard.tsx`, `QuotaMiniBar.tsx`,
  `parts/QuotaCardExpanded.tsx`). Antigravity has a dedicated family view: Gemini and Claude & GPT, each with a
  session and a weekly window (`AntigravityQuotaGroups.tsx`, `antigravityWeeklyQuota.ts:21-41`).
- **Status:** remaining > 50 % ok, > 20 % alert, else critical (`ProviderLimits/utils.tsx:405-415`). Filters by
  status, tier (enterprise … free), provider, environment; full or compact layout; all kept in localStorage
  (`ProviderLimits/index.tsx:47-57,221-241`, `constants.ts:48-59`).
- **Refresh:** per-card refresh with a 30 s client floor (`index.tsx:52,383`), "refresh all"
  (`POST /api/usage/provider-limits`, `index.tsx:460-482`), and an optional auto-refresh that is **off by default**,
  180 s when enabled, and runs only while the tab is visible (`quota/page.tsx:8-9`, `index.tsx:488-512`).
- **Server side:** cached results ("provider limits cache") refreshed by a background scheduler every **70 minutes**
  by default (`src/lib/usage/providerLimits.ts:114,654-655`; `src/shared/services/providerLimitsSyncScheduler.ts:8,41-66`).
  OAuth connections are synced **strictly sequentially**, 1500 ms apart, "so a single host never bursts simultaneous
  usage/refresh requests to the same upstream" (`providerLimits.ts:663,1033-1053`). A **post-usage refresh** runs 5 s
  after a connection serves a request, deduplicated per connection (`providerLimits.ts:116-135`).
- **Throttle:** a global gate spaces every upstream quota call ≥ 250 ms (+ jitter), citing that bursts "look like
  automation to the upstream" and can get a Codex token revoked (`open-sse/services/quotaFetchThrottle.ts:1-19`;
  the cited issue is CLIProxyAPI#2385, "Codex batch refresh at startup causes refresh_token_reused 401",
  `gh api repos/router-for-me/CLIProxyAPI/issues/2385`).
- Per-fetch caches of 60 s to 5 min with in-flight deduplication (`antigravity.ts:70-78`,
  `antigravityWeeklyQuota.ts:43`, `codexQuotaFetcher.ts:52`).

**Useful:** the family×window view for Antigravity; plan label; remaining % with reset countdown; three-band colour;
cached snapshot with a background refresh; sequential, spaced OAuth polling; post-usage refresh (cheap freshness);
"unknown" distinct from 0 %; stale-on-429.

**Noise:** about 80 providers (`supportedProviders.ts`); quota-share pools, burn-rate charts, allocation tables
(`dashboard/costs/quota-share/*`); per-window cutoff thresholds and quota preflight scoring
(`QuotaCutoffModal.tsx`, `quotaPreflight.ts`); a session quota monitor with 60 s/15 s adaptive polling
(`quotaMonitor.ts:1-25`); Codex reset-credit redemption (`CodexResetCreditsModal.tsx`,
`useCodexResetCreditRedemption.ts`); credit-spending balance probes for Antigravity
(`antigravity.ts:595-609`); synthetic "local usage" estimates written over upstream numbers
(`antigravity.ts:120-182`); tier, environment and provider filter matrices.

## 5. Recommended minimal feature set for remora

### Providers, in order

1. **Antigravity**: `retrieveUserQuotaSummary` (family × 5 h/weekly) + `loadCodeAssist` (plan). Add
   `retrieveUserQuota` per-model buckets only if the summary call fails for an account (it is "optional,
   undocumented", `antigravityWeeklyQuota.ts:3-7`). Skip `fetchAvailableModels` for quota (stale by OmniRoute's own
   account).
2. **Codex**: passive `x-codex-*` signals from `GET /credentials` first; poll `wham/usage` only when the snapshot is
   older than the poll interval.
3. **Claude**: passive `anthropic-ratelimit-unified-*` first; poll `api/oauth/usage` only when stale.
4. **Kimi, Grok** (`/coding/v1/usages`, `/v1/billing?format=credits`): later, same mechanism, one parser each.
5. **Qwen, iFlow, others:** no quota endpoint. Show engine cooldowns only and label them "quota not reported".

### Data model (remora store, one row per account; overwritten, no history)

```
AccountQuota {
  account_id      // remora account
  plan            // "free" | "pro" | "ultra" | "plus" | ... or "" when unknown
  windows: [      // one per (scope, window)
    { scope       // "gemini" | "claude_gpt" (antigravity family), model id, or "" for account-wide
      window      // "5h" | "weekly" | "monthly" | duration from limit_window_seconds
      remaining   // fraction 0..1, null = unknown (never coerce to 0)
      reset_at    // time or null
    } ]
  limit_reached   // bool, codex/claude when reported
  source          // "passive" | "poll"
  fetched_at      // when this snapshot was observed upstream
  error           // last fetch error ("reauth needed", "rate limited", ...) while keeping the last good windows
}
```

Fold it into the existing `Account.quota` in `api/openapi.yaml:1151-1184`. Today that holds `{model,
remaining_fraction, reset_at}`; add `window`, `scope`, `plan`, `fetched_at` and `error`. Keep the cooldown-derived
entries that `adapters.go:590-621` already produces. A percentage, not used/limit counts: no subscription endpoint
above returns real counts except Kimi, and OmniRoute's `total = 1000` is invented (`antigravityWeeklyQuota.ts:164`).

### Fetching

- One `internal/quota` package with a fetcher per provider. It calls `cliproxyapi.Client.APICall(ctx, authIndex,
  method, url, headers, body)` → `POST /v8/management/requests/api-call`, then parses the body in Go. Table tests use
  recorded bodies; e2e uses a fake upstream (api-call accepts any URL, `api_tools.go:117-127`, so the fakes image can
  serve the probe).
- **Poll:** default every **15 min**, configurable, **minimum 5 min**. Walk accounts **sequentially** with ≥ 2 s plus
  jitter between upstream calls (OmniRoute's 1.5 s spacing plus a margin, `providerLimits.ts:663,1033`). With 20
  Antigravity accounts and 2 calls each, that is about 80 s per cycle and ~160 calls an hour: gentle.
- **Skip:** disabled accounts; accounts whose passive snapshot is younger than the interval (codex, claude);
  accounts the engine marks `unavailable` for auth reasons. Poll an account whose window is exhausted **once after its
  `reset_at`**, not every cycle.
- **On demand:** a per-account "refresh" button and "refresh all" in the UI, both through the same sequential queue
  and a **60 s per-account floor**, so a button cannot become a load test.
- **Backoff:** on upstream 429 or 5xx, double that account's interval up to 4 h and keep the last good snapshot with
  `error` set. On 401/403, call `POST /credentials/refresh` once (`server_management_v8.go:50`), retry once, then mark
  "reauth needed" and stop polling it until the account changes.
- **Start-up:** no burst at boot. Spread the first cycle over one interval (the lesson of CLIProxyAPI#2385).
- Never poll from tests against real upstreams; the fakes only (`AGENTS.md`).

### Tie-in with cooling

- **Display:** the page shows the engine's per-account cooldowns (`cooldowns`, `next_retry_after`) next to the
  quota windows, because that is what actually removes an account from rotation. The engine already does
  per-account, per-model cooldowns with upstream retry delays (`docs/research/2026-10-14-oauth-engines.md:21`).
  remora must not duplicate that.
- **One integration, phase 2:** when every enabled account of a subscription provider reports `remaining = 0` for the
  family serving an alias member (e.g. all Antigravity accounts' Claude & GPT weekly window), cool that alias member
  in `internal/cooling` until the **earliest `reset_at`** among them, instead of `DefaultSubscriptionCooldown`.
  Remove the member preemptively instead of waiting for 429s. That needs one new entry point on `Cooler`, e.g.
  `CoolUntil(target, until, reason)`, beside `Observe` (`internal/cooling/cooling.go:99-112`). Cooling stays
  advisory: a stale or unknown quota never cools anything.

### The page ("Provider Quota", under Providers or the Overview)

- One dense table grouped by provider, a row per account: email/label, plan chip, one compact bar per window
  (Antigravity: Gemini 5 h | Gemini weekly | Claude & GPT 5 h | Claude & GPT weekly; Codex: 5 h | weekly [+ per-model];
  Claude: 5 h | weekly [+ opus/sonnet]), remaining % and reset countdown on each bar, cooldown chip, "updated
  N min ago", error text, refresh button.
- Header per provider: count of accounts available now / exhausted / reauth needed, and the **next reset** across
  the pool. That is the one aggregate that answers "when does capacity come back".
- Colours: > 50 % ok, 20-50 % warn, < 20 % critical, grey for unknown. Sort by soonest reset as an option.
- Paged, filtered and searched by default, like every list (it reuses the existing data-list component).

### Explicitly not building (noise)

- **Quota-share pools, allocation tables, burn-rate charts**: capacity planning for resellers; the owner runs one pool.
- **Quota history / time series**: one overwritten snapshot per account answers every question the page asks.
- **Per-window cutoff thresholds and quota preflight scoring**: routing policy duplicates the engine's cooldowns; a
  second scheduler is the class of bug that cost the reference gateway 1,500 calls a day.
- **Adaptive per-session polling (60 s / 15 s)**: that is exactly the upstream load that gets tokens flagged.
- **Credit-spending balance probes** (Antigravity credits mode): spends real quota to measure quota.
- **Codex reset-credit redemption**: a destructive account action, not monitoring.
- **Local usage estimates overwriting upstream numbers**: invented precision. Show "unknown" instead.
- **`fetchAvailableModels` as a quota source**: OmniRoute documents that it stays full after real usage.
- **Engine quota plugins or `quota_probe` metadata**: third-party code in the engine, or a v0-only flat mapper.
- **Tier, environment and provider filter matrices, layout toggles**: one grouped table with search covers 20-30
  accounts.
- **Providers with no quota endpoint (Qwen, iFlow)**: nothing to fetch. Cooldowns already cover them.
- **Alerts or notifications on low quota**: not asked for; the page and the cooling hint cover it.

### Exact calls remora would make

Engine (management secret, loopback):

- `GET /v8/management/credentials`: identities (`auth_index`, `project_id`, `id_token.chatgpt_account_id`,
  `id_token.plan_type`), passive `quota.signals` / `model_quotas`, `cooldowns`, `next_retry_after`, `status`.
- `POST /v8/management/requests/api-call`: every upstream probe, with `Authorization: Bearer $TOKEN$`.
- `POST /v8/management/credentials/refresh`: once, on 401/403 before giving up.
- `POST /v8/management/routing/cooldown/reset`: already used.

Upstream (via api-call):

- Antigravity: `POST https://daily-cloudcode-pa.googleapis.com/v1internal:retrieveUserQuotaSummary` (fallback
  `https://cloudcode-pa.googleapis.com/...`), body `{"project":"<project_id>"}`;
  `POST https://cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` for the plan (cache ≥ 6 h); fallback
  `POST .../v1internal:retrieveUserQuota`.

### Risks

- All upstream endpoints are private and unversioned. Parsers must be lenient and fail to "unknown".
- User-Agent and client-version headers matter (Antigravity < 2.23.0 is refused; Grok < 1.0.13 is refused,
  console `constants.ts:77-79,155-156`). Mirror the engine's own UA, and re-check on every engine bump.
- Codex `metadata.access_token` is used as stored (`api_tools.go:293`). If the engine has not refreshed it yet, the
  probe gets 401. That is the reason for the refresh-once rule.
