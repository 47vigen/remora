# remora 0.1: design

Date: 2026-10-14. Status: draft for owner review.
Repository: `github.com/47vigen/remora`, public from the first commit, Apache-2.0.
Research behind every decision: [`docs/research/`](../research/README.md).

## Intent

remora is an open-source LLM gateway that does not build its own engines. It rides on actively maintained
upstream projects, the way a remora rides a shark, and presents them as one coherent product with one API, one
UI and one configuration model.

It exists because the gateways that cover everything a real deployment needs (subscription OAuth accounts,
free-tier pooling, cross-provider fallback, embeddings, speech-to-text, decision models, per-key policy) are
heavy, slow to operate and accumulate their own bugs. The ones that are light and fast each cover only part of
it. remora composes the best part of each and owns only the seams.

The first user is the owner's own production gateway (an OmniRoute 3.8.51 serving five services, about 8k
requests a day). remora 0.1 is done when it can replace that gateway completely. From then on it should be a
project anyone can install and use, and that others can contribute to.

### Why now

- The reference gateway is about 1 GB of RAM and a 490 MB SQLite file for a workload that needs a fraction of it,
  and it has bugs that cost real traffic (about 1,500 failed calls a day from one cooldown bug, Persian
  half-spaces stripped from every response). See
  [the reference deployment](../research/2026-10-14-reference-deployment.md).
- Bifrost and CLIProxyAPI matured enough in 2026 to carry the hard parts, and decision models arrived as a new
  API shape that the reference gateway does not support at all.

### What success looks like

1. All five reference consumers run on remora with no loss of capability, and the old gateway is removed.
2. A stranger can run `docker run ghcr.io/47vigen/remora`, open the UI, add a provider, log into a subscription
   account, create a key and send a request, without ever reading the words Bifrost or CLIProxyAPI outside the
   credits.
3. Following upstream is a green pull request, not a merge.

## Goals

- **One product surface.** One exposed port, one HTTP API (OpenAI-compatible inference plus remora's management
  API), one web UI, one configuration model. Users never see, configure or authenticate against an engine.
- **Engines stay upstream.** Engines are git submodules built from source. remora contains no copy of engine
  code and no long-lived patches. A patch, when unavoidable, lives in a fork only until upstream merges it.
- **Full parity with the reference deployment** (the "MUST" and "MUST NOT" lists in
  [the reference deployment](../research/2026-10-14-reference-deployment.md)), including capabilities and
  providers that are configured there but idle.
- **Free first, paid second.** Aliases chain free and subscription capacity ahead of paid providers, and move on
  when a member answers 429 or 402.
- **Small and fast to operate.** One image, low memory, fast startup, no external database required.
- **A project built to grow.** Clean structure, contracts first (OpenAPI), tests that exercise the real image,
  automated releases, documentation good enough for contributors.

## Non-goals for 0.1

- Multi-user accounts, roles, OIDC. One admin.
- Budgets and rate limits per key (the engine supports them; remora exposes them later).
- Postgres, clustering, more than one replica.
- MCP gateway, guardrails, semantic caching, prompt management.
- Gemini CLI OAuth (the OAuth engine does not support it; Antigravity covers Gemini).
- Cline OAuth: neither engine supports it, and the reference account is idle and out of credit. Recorded as an
  exception in `docs/parity.md` rather than built outside the engines.
- A Kubernetes operator or Helm chart.
- Internationalised UI (English only, left to right).

## Anti-goals

These would make remora a failure even if it worked:

- **Becoming another OmniRoute**: re-implementing what an engine already does, or forking an engine and drifting.
- **Leaking the engines**: an engine's name, UI, port, error format or credential reaching a user.
- **Configuration in two places**: any setting a user must make in an engine rather than in remora.
- **Silent behaviour changes**: dropping a parameter, rewriting text, swallowing an error, or answering from a
  model the client did not ask for without saying so.
- **A personal project in public**: any host name, product name, key or deployment detail of the owner in the
  repository.

## Architecture

```
                         one port (default 8080)
client ──► remora ──┬── /v1/*  inference proxy ──► Bifrost (127.0.0.1) ──┬── API-key providers (OpenRouter, ...)
                    │                                                     ├── CLIProxyAPI (127.0.0.1) ──► Antigravity, Codex, Grok, ...
                    │                                                     └── Soniox adapter (127.0.0.1, inside remora) ──► Soniox
                    ├── /api/*  management API (OpenAPI)
                    └── /       web UI (embedded)
```

### Components

| component | what it owns | origin |
|---|---|---|
| **remora** (Go binary) | the only exposed listener; client authentication and alias-level allowlists; aliases and their compilation into engine routing; `/v1/models`; the management API; the UI; the store; supervising engine processes; the Soniox adapter | this repository |
| **Bifrost** | inference routing and same-request fallback across providers; API-key providers; embeddings; transcription transport; decisions (`/v1/decisions`, `/v1/systemone`); request logs and analytics | submodule `engines/bifrost`, `maximhq/bifrost` |
| **CLIProxyAPI** | subscription OAuth accounts (Antigravity, Codex, Grok and the rest it supports), account pooling, token refresh, per-account cooldown and quota | submodule `engines/cliproxyapi`, `router-for-me/CLIProxyAPI` |

Why these engines and not others, with evidence:
[front door: Bifrost](../research/2026-10-14-front-door-bifrost.md),
[front door: agentgateway](../research/2026-10-14-front-door-agentgateway.md),
[OAuth engines](../research/2026-10-14-oauth-engines.md),
[the gaps](../research/2026-10-14-gaps-voice-embeddings-decisions.md).

### Packaging: one image, several processes

One container image built entirely from source by a multi-stage Dockerfile: a Bun stage builds the UI, Go stages
build remora (with the UI embedded via `go:embed`), Bifrost (with an empty `ui/` stub so its dashboard is never
built or served) and CLIProxyAPI (cgo on). The runtime base is glibc (CLIProxyAPI's plugin host requires it), with
`tini` as PID 1 and remora as the supervisor. Images are multi-arch (amd64, arm64).

A single binary was considered and rejected: both engines have closed provider sets, the OAuth engine's
executors are not importable, and linking two TLS stacks into one Rust binary is a risk with no benefit. Loopback
HTTP costs microseconds against upstream latencies of seconds. See
[composition](../research/2026-10-14-composition.md).

### Process supervision

remora starts the engines as child processes, each bound to `127.0.0.1` on a port remora chooses, with
credentials remora generates at first boot and keeps in its store. It waits for each engine's health endpoint
before opening its own listener, restarts a crashed engine with backoff, forwards signals, and shuts children down
in order. `remora` refuses to start if an engine binary is missing or its version is not the one the image was
built with.

### Data

Everything lives under one volume, `/data`:

```
/data/remora.db          remora's store (SQLite) — the source of truth
/data/bifrost/           Bifrost's config store and log store (SQLite)
/data/cliproxyapi/       CLIProxyAPI's config and auth-dir (OAuth credential files)
```

## The single surface

### Inference: `/v1/*`

remora authenticates the client key, reads the requested `model` (from the JSON body, or the multipart `model`
field), checks it against the key's allowlist **as the client wrote it**, and forwards the request to Bifrost with
the internal credential that belongs to that key.

A client may name either an **alias** (a remora name with a fallback chain) or a **provider model**
(`<provider>/<model>`, served directly by that provider with no fallback). Existing consumers keep working with the
raw names they already send. An allowlist entry matches either form and accepts globs (`fast`, `antigravity/*`).
`/v1/models` lists aliases only. Bodies are streamed through; remora never buffers a stream or
rewrites content. Endpoints:

| endpoint | notes |
|---|---|
| `POST /v1/chat/completions` | stream and non-stream, tools, `response_format`, reasoning effort, images |
| `POST /v1/responses` (+ WebSocket) | Codex-style clients |
| `POST /v1/messages` | Anthropic-style clients |
| `POST /v1/embeddings` | `dimensions`, batched input, `encoding_format: base64` |
| `POST /v1/audio/transcriptions` | multipart; Soniox via the adapter, others via the engine |
| `POST /v1/decisions`, `POST /v1/systemone` | decision models, both wire formats |
| `GET /v1/models` | served by remora itself, see below |

Errors use the error shape of the endpoint's own API: OpenAI's on the OpenAI endpoints, Anthropic's on
`/v1/messages`, TypeSafe's on `/v1/systemone`, so each client SDK can parse them. An engine's own error body is
passed through only when it already has that shape and names no engine; otherwise remora maps it.

Every response carries the model that actually served it in `model`, and remora adds `x-remora-alias`,
`x-remora-served-by` and `x-remora-fallback` headers.

**Known engine rewrites are announced, never silent.** The OAuth engine's Codex translator drops `temperature`,
`top_p` and `max_tokens`/`max_output_tokens` (and, on chat, a few more such as `stop`, `user`, `top_k`) and always
sets `parallel_tool_calls: true` (the Codex backend does not accept the dropped ones on its reasoning models). When
a Codex member serves a request that carried any of these, remora adds `x-remora-dropped-params` listing every one
it dropped. The behaviour is documented in the README and in
`docs/parity.md`. Any other engine rewrite found later gets the same treatment.

### Keys

Keys belong to remora. A key has a name, a value, an allowlist (aliases and provider models, globs allowed) and an
enabled flag. remora stores only a hash and shows a generated value once. For each remora key, remora maintains
one internal Bifrost virtual key whose value never leaves the container, so engine logs and analytics are still
per key.

remora accepts any key value it stores, so `remora import omniroute` keeps every imported key's exact value and
consumers change only their base URL. No engine prefix (such as `sk-bf-`) ever reaches a user.

### Aliases

An alias is a name clients use as `model`. It has an ordered list of members; a member is either a provider model
(`<provider>/<model>`) or another alias. Nesting is allowed; cycles are rejected; the depth is capped (default 5).
Per alias: capabilities to advertise (used by `/v1/models`, including `supported_parameters` such as
`structured_outputs`), an optional context-window override, and the kind of endpoint it serves (chat, embeddings,
transcription, decisions).

remora compiles each alias into a flat chain (nested aliases expanded in order, duplicates removed) and applies it
to Bifrost as one routing rule: the first member as the target, the rest as fallbacks. The engine falls over on
any error except a cancelled request (so 429, 402, `insufficient_quota`, 5xx and transport errors, but also a 400
from one member); it has no setting to narrow that. The UI shows the compiled chain next to the definition.

Allowlist and alias globs: `*` matches any name, and a trailing `/*` matches any depth below it
(`openrouter/*` matches `openrouter/qwen/qwen3-embedding`); otherwise `path.Match` rules apply.

**Skipping dead members across requests.** The open-source engine remembers a failed member only within one
request. The engine has no live log stream (its WebSocket broadcasts store changes only), so remora tails the
engine's log store by polling; when a member returns 402, or 429 several times in a short
window, remora marks it cooling (honouring `Retry-After` when present), recompiles the affected aliases without
it, and restores it when the cooldown ends. Cooling members are visible in the UI. Per-account cooldowns inside
the OAuth engine stay the OAuth engine's job.

### `/v1/models`

Served by remora, never proxied. It lists the aliases the calling key may use, with `context_length` and
`supported_parameters` from the alias definition. No raw provider catalogue is exposed.

### Providers

| kind | how it is added | engine |
|---|---|---|
| API key: OpenRouter, OpenAI-compatible (any base URL), and the providers Bifrost ships | name, base URL if custom, one or more keys | Bifrost |
| Subscription OAuth: Antigravity, Codex, Grok, and the rest CLIProxyAPI supports | an account login flow, several accounts per provider pooled | CLIProxyAPI |
| Soniox | API key | the adapter inside remora |
| Decision providers (TypeSafe-compatible base URLs such as Experiential and OpenRouter; OpenAI for `/v1/decisions`) | name, base URL, key | Bifrost |

CLIProxyAPI is registered in Bifrost once, as an internal OpenAI-compatible provider with the completions,
responses and messages formats. Users see each OAuth provider as its own provider in remora.

**OAuth login from a remote browser.** The providers redirect to `localhost` on the server, which the user's
browser cannot reach. remora's UI shows the login link; the user signs in, lands on a page that does not load,
and pastes that page's full address into remora. remora completes the exchange through the engine and shows the
account's status. Device-code providers (Grok) show a link and a code and complete on their own.

### Speech-to-text: the Soniox adapter

Part of the remora binary, listening on an internal loopback port, registered in Bifrost as a custom provider
`soniox`. It accepts OpenAI-style multipart transcription requests and runs Soniox's async API: upload, create the
transcription (with `enable_speaker_diarization`, `context`, `language_hints` passed through and booleans parsed),
poll with a bounded interval and an overall deadline, fetch, and delete the transcription and the file in a
`finally` path. It returns OpenAI `verbose_json` with `text`, `language`, `duration`, `words`, and `segments`
grouped by speaker (`id`, `speaker`, `start`, `end`, `text`). A periodic sweep deletes any Soniox file or
transcription older than one hour that remora created, so a crash cannot fill the account's quota. Unknown
parameters are forwarded or rejected with a clear error, never dropped.

The engine currently drops `speaker` from transcription segments when it relays a provider's response. remora
fixes this with a one-field upstream pull request; until it merges, the submodule points at the owner's fork and
the patch is listed in `docs/patches.md`.

### Management API: `/api/*`

Contract first: `api/openapi.yaml` is the source; the Go server interfaces are generated with `oapi-codegen`, the
UI client with `@hey-api/openapi-ts` (TanStack Query hooks). Resources:

| resource | operations |
|---|---|
| providers | list, create, update, delete, test |
| accounts (OAuth) | start login, complete login (pasted URL), poll status, list with quota/cooldown/models, enable/disable, delete, reset cooldown |
| aliases | list, create, update, delete, compiled chain, cooling members |
| keys | list, create (value shown once), update allowlist, enable/disable, delete, usage |
| logs | list with filters (key, alias, served model, provider, status, time range, text), detail with fallback path, live mode (a WebSocket from remora, fed by tailing the engine's log store) |
| stats | volume, error rate, latency percentiles, tokens, cost, by key/alias/provider over a time range |
| settings | admin password, API token, export, import |
| system | health, version (remora and each engine) |

remora drives the engines only through their runtime management APIs (see
[the API map](../research/2026-10-14-engine-management-apis.md)). Engine configuration files hold only bootstrap
values (internal ports, credentials, storage paths) and are rewritten from the store on every boot, because the
OAuth engine takes its port only from its file; every change to providers, keys, aliases or accounts is an API
call, with no restart. If an engine call fails, remora's store change is rolled back and the error is returned.

**Reconciliation.** On startup and on a timer, remora compares its store with each engine's state and corrects
the engine. The store wins; nothing in an engine survives that remora does not know about.

### Source of truth and GitOps

remora's SQLite store is the only source of truth. The UI and the API edit it. `remora export` writes the whole
configuration (without secrets, which are referenced by name) as `remora.yaml`; `remora apply -f remora.yaml`
makes the store match a file, showing a diff first; `remora import omniroute <data-dir>` converts an OmniRoute
installation (providers, OAuth accounts, keys, combos as aliases; see
[migrating from OmniRoute](../research/2026-10-14-migrating-from-omniroute.md)). Secrets in a file are given as
`env:NAME` references.

### Authentication

One admin. At first boot (no admin in the store) the password comes from `REMORA_ADMIN_PASSWORD`, or remora
generates one and prints it once to the log; after that the stored password wins and is changed in Settings.
Secrets at rest (provider keys) are encrypted with a master key from `REMORA_MASTER_KEY`, or a generated
`$REMORA_DATA/master.key`. The UI uses a secure, HTTP-only session cookie. Scripts use an API token (created
in Settings) as a bearer token on `/api/*`. Client keys work only on `/v1/*`.

## The UI

Vite, Bun, React 19, TypeScript, HeroUI v3 on Tailwind v4, TanStack Router and TanStack Query, the generated API
client. **No custom CSS and no custom theme**: HeroUI's own components, tokens, light and dark modes. English,
left to right. Built into the binary; no Node at runtime.

Pages:

1. **Overview**: last 24 h of volume, error rate, p50/p95 latency, tokens and cost; provider and account health;
   cooling members.
2. **Providers**: API-key and OAuth providers in one list; add, edit, test; for OAuth providers, their accounts
   with login, status, quota, cooldown and models.
3. **Aliases**: definition with ordered members (drag to reorder, nested aliases allowed), capabilities and
   context override; the compiled chain beside it.
4. **Keys**: create (value shown once), allowlist, enable/disable, per-key usage.
5. **Logs**: paged, filtered and searchable list; detail with request, response, the fallback path and timing;
   live mode.
6. **Settings**: admin password, API token, export and import.

Every list is paged, filterable and searchable.

**Code taken from Bifrost's UI**, once and never synced: provider icons and metadata, log constants, chart and
export helpers, the recharts chart code and log column formatters re-rendered on HeroUI, and the live-log
WebSocket logic. Each copied file starts with `// Derived from maximhq/bifrost ui/<path> (Apache-2.0); modified.`
and `THIRD_PARTY_NOTICES.md` credits it. No brand strings or images are copied. See
[UI reuse](../research/2026-10-14-bifrost-ui-reuse.md).

## Engineering practice

- **Pull requests only** to `main`, Conventional Commits with scopes (`feat(alias):`, `fix(proxy):`).
- **CI on every pull request** (GitHub Actions): `golangci-lint`, `go test -race`, UI lint and typecheck, OpenAPI
  generation drift check, image build, and the end-to-end suite against the built image.
- **End-to-end suite** (fake upstreams, no real keys): chat stream and non-stream with Persian text containing
  half-spaces (bytes compared), one id per stream, usage in the final chunk; `json_schema`; tools in a stream;
  fallback on 429 and 402 across providers in one request; nested alias compilation; alias allowlist enforcement;
  `/v1/models` contents; embeddings with `dimensions` and base64; transcription through the Soniox fake with
  segments, speakers and deletion verified; decisions on both endpoints with fallback; cooling and recovery of a
  dead member; reconciliation after an engine restart.
- **Release**: `release-please` writes the changelog and tags semver; the release workflow publishes
  `ghcr.io/47vigen/remora` for amd64 and arm64 with an SBOM, signed with `cosign`, and a GitHub release.
- **Following upstream**: a scheduled workflow moves each engine submodule to its latest release tag and opens a
  pull request; it merges only when the end-to-end suite is green. Each release notes the engine versions inside.
- **Patches**: `docs/patches.md` lists every engine patch with its upstream pull request; the submodule returns to
  upstream when it merges.
- **Open-source hygiene**: README with a quick start, a plain statement about the terms of service of
  subscription providers, credits to the engines; CONTRIBUTING, SECURITY (private reporting), CODE_OF_CONDUCT,
  issue and PR templates, CODEOWNERS; `THIRD_PARTY_NOTICES.md`; no owner hosts, domains, product names or secrets
  anywhere.

## Definition of done for 0.1

1. `docs/parity.md` lists every capability, provider, endpoint and behaviour of the reference deployment (derived
   from its live configuration), each with the test or check that proves it. All are green, except items that can
   only be proven against real subscription accounts, which are proven in the migration's first step and recorded,
   and the recorded exceptions (Cline OAuth; clustering, a non-goal of 0.1). The public file is generic: capabilities, provider kinds, endpoints,
   behaviours. Deployment specifics (account identities, host names, the real alias set) live in the private
   migration runbook outside this repository.
2. The end-to-end suite above is green in CI on the released image.
3. A clean machine can run the quick start from the README to a successful request.
4. The reference deployment has fully migrated (the migration runbook lives outside this repository).

## Left to the builder

- Internal port numbers, timeouts, poll intervals and backoff values (with sensible defaults, all overridable).
- The SQLite schema and migration tool.
- The exact layout of `remora.yaml`, as long as export → apply is a round trip.
- How remora maps engine errors to OpenAI-shaped errors, as long as no engine name leaks.
- How the e2e suite starts the image (Docker in CI is expected).
- Plan breakdown and order (in `docs/plans/`).
