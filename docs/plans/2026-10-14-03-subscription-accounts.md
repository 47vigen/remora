# Subscription Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the OAuth engine behind the front door. This covers account login, status and lifecycle, the `x-remora-dropped-params` header for Codex, and cooling of dead alias members, so that plan 05 only has to add HTTP handlers.

**Architecture:** `internal/engine/cliproxyapi.Client` drives the OAuth engine's v8 management API. `internal/accounts.Service` combines that client with a new `accounts` table, which is remora's view of the accounts, and owns login, lifecycle and reconciliation. The OAuth engine is registered in the front door once, as the internal custom provider `remora-oauth`. Every OAuth credential carries the engine-side `prefix` `<provider>`, so the user-facing reference `codex/gpt-6-luna` is also the exact model id the OAuth engine routes on. `internal/cooling` follows the front door's log rows through a poller (`bifrost.Tail`), cools members after a 402 or repeated 429s, and asks reconcile to recompile.

**Tech Stack:** Go 1.27, `net/http`, `log/slog`, `database/sql` (SQLite, plan 01), `httptest`, Docker Compose e2e (plan 01).

**Spec:** `docs/specs/2026-10-14-remora-0.1-design.md` (sections: Providers, OAuth login from a remote browser, Known engine rewrites, Skipping dead members, Reconciliation). Research: `docs/research/2026-10-14-oauth-engines.md`, `docs/research/2026-10-14-engine-management-apis.md`.

Engine versions verified: CLIProxyAPI `v8.0.28` (`0d18d3b`), Bifrost `dev` at `72457fe`. Paths below are relative to each engine's root: `C/` = CLIProxyAPI, `B/` = Bifrost.

## Global Constraints

- Go module `github.com/47vigen/remora`, Go 1.27. Engines are never imported. They are reached only over loopback HTTP.
- OAuth engine loopback address: `127.0.0.1:18317` (`REMORA_PORT_ACCOUNTS` overrides it; `config.Config.Ports.CLIProxyAPI` in Go). The management secret is generated by plan 01 and kept in the store.
- **Leaking the engines is an anti-goal.** No engine name, port, error format or credential may reach a user. This covers errors, headers, account fields and log text. The internal provider name `remora-oauth` and the internal client key never leave the container.
- remora drives the engines only through their runtime management APIs, with no restarts. If an engine call fails, the store change is rolled back and the error is returned.
- The store is the source of truth. Reconciliation runs on startup and on a timer, and the store wins.
- `x-remora-dropped-params`: a comma-separated list, sent only when it is non-empty, and only when a Codex member served the request.
- Cooling: a 402 cools a member at once. 429 three times within 60 s cools it. `Retry-After` is honoured, and the default cooldown is 5 min. Every value can be overridden.
- Per-account cooldowns inside the OAuth engine stay the OAuth engine's job.
- Tests: `go test -race ./...`. e2e tests sit behind the build tag `e2e`. Engine contract tests sit behind the build tag `engine`. No real provider, account or key is ever used.
- Code style: `log/slog`, errors wrapped with `%w`, `context.Context` first, no global state, table-driven tests.
- Commits: Conventional Commits with scopes, on the plan branch. No owner host, domain, product name or secret appears anywhere.

## Review Focus

1. **A pasted address from the wrong tab or login.** This includes a URL whose `state` belongs to a different login, a URL with no `code`, plain text, or the device-flow state. The user expects a clear "this is not the sign-in address for this login" error, and the engine must not be called. Test: Task 3, `TestCompleteLoginRejectsBadRedirect`.
2. **Every member of an alias is cooling.** The user expects the alias to keep serving its full chain and not to become an empty or missing route. Test: Task 9, `TestFilterKeepsChainWhenAllCooling`.
3. **The engine restarts mid-login.** The engine forgets its in-memory sessions. The user expects "login expired, start again", not `wait` forever. Test: Task 3, `TestLoginStatusExpired`.
4. **A credential that just finished logging in meets a reconcile pass before it is adopted.** The user expects the new account to survive. Test: Task 5, `TestReconcileKeepsPendingLoginCredential`.
5. **A long request whose error row is written late**, with a timestamp older than rows already seen. The user expects its 429 or 402 still to count. Test: Task 8, `TestTailCatchesLateRow`.

```go
type Service struct{ /* engine *cliproxyapi.Client; store *store.Store; log *slog.Logger; now func() time.Time; mu; pending map[string]*pending */ }

var (

    ErrLoginNotFound   = errors.New("login not found")          // state never started here
    ErrLoginExpired    = errors.New("login expired, start again")
    ErrBadRedirect     = errors.New("this is not the sign-in address for this login")
    ErrNotPasteFlow    = errors.New("this login completes on its own")
)
// login.go
type Login struct{ State, Provider, URL, Mode, UserCode string; ExpiresAt time.Time } // Mode "paste" | "device"
type LoginStatus struct{ Status, Message string; Account *Account }                 // Status "wait" | "ok" | "error"
func (s *Service) StartLogin(ctx context.Context, provider string) (Login, error)
func (s *Service) CompleteLogin(ctx context.Context, state, redirectURL string) error
func (s *Service) LoginStatus(ctx context.Context, state string) (LoginStatus, error)
func (s *Service) CancelLogin(ctx context.Context, state string) error
func (s *Service) PendingProviders() map[string]bool // engine provider ids with a login not yet adopted (Task 5)
```

The `Account` type is defined in Task 4. Declare it here as `type Account struct{ store.Account; /* engine fields, Task 4 */ }` so this task compiles.

Behaviour that the signatures leave open:
- `StartLogin` calls the engine without `is_webui`. That flag would start a callback forwarder inside the container (`auth_files_oauth_callback.go:28`), which a remote browser cannot reach. If the response has `flow == "device"`, Mode is `device`; otherwise Mode is `paste`. `ExpiresAt = now + expires_in`. When `expires_in` is absent, use the engine's session TTL of 30 min (`oauth_sessions.go:18`). Record the login as pending: state, provider and mode.
- `CompleteLogin` trims the address. Then it requires all of these: `url.Parse` succeeds, the query has `code` or `error`, and the query's `state` is either empty or equal to `state`. Otherwise it returns `ErrBadRedirect` without calling the engine. A device login returns `ErrNotPasteFlow`. The engine's 404 "unknown or expired state" maps to `ErrLoginExpired`.
- `LoginStatus` maps the engine's `error` with the message `unknown or expired state` to `ErrLoginExpired`. On `ok`, under the mutex, it adopts every credential whose `Provider` is the login's engine ID and is not in the store. For each one it calls `SetCredentialPrefix(name, Provider.Name)` and then `CreateAccount{Provider: Name, Label: Email or Label, Credential: Name, Enabled: true}`. It returns the provider's credential with the newest `UpdatedAt`. Signing in again to an existing account rewrites the same file, so in that case nothing new is adopted, but the returned account is still the right one. The done result stays readable until the 30-min TTL, so a repeated call returns the same `ok`.

### Task 4: Account list, enable, delete, cooldown reset, import

**Files:**
- Create: `internal/accounts/{manage.go,manage_test.go}`

**Interfaces:**
- Consumes: Task 3 `Service`, Task 1 client, Task 2 store.
- Produces:

```go
type Account struct {
    store.Account
    Status, StatusMessage string        // engine status; "missing" when the engine has no such credential
    Unavailable           bool
    NextRetryAfter        *time.Time
    Cooldowns             []cliproxyapi.Cooldown
    Quota                 map[string]string // Quota.Signals, opaque per provider
    Success, Failed       int64
    Models                []string          // user refs, "<provider>/<model>"
}
var ErrNotFound = errors.New("account not found")
func (s *Service) List(ctx context.Context, provider string) ([]Account, error) // "" = all
func (s *Service) SetEnabled(ctx context.Context, id int64, enabled bool) error
func (s *Service) Delete(ctx context.Context, id int64) error
func (s *Service) ResetCooldown(ctx context.Context, id int64) error
func (s *Service) Import(ctx context.Context, provider string, credential []byte) (Account, error) // used by plan 05 import
```

Behaviour:
- **Order of writes.** Every mutation calls the engine first and changes the store only when the engine call succeeds.
  - `SetEnabled` sends `SetCredentialDisabled(!enabled)`.
  - `Delete` sends `DeleteCredential`. An engine 404 counts as already gone, and the store row is deleted anyway.
  - `ResetCooldown` reads `auth_index` from `Credentials` and sends `ResetCooldown(authIndex)`.
- **Import.** The credential must be a JSON object. The file name is `<provider>-<random 8 hex>.json`. The store row is inserted *before* the upload, so a reconcile pass cannot delete the credential. If the upload or `SetCredentialPrefix` fails, the row is deleted and the error is returned.
- **Models.** Model IDs come from `CredentialModels`. Any ID that lacks the `<provider>/` prefix gets it added.

```go
type Config struct {

    Window    time.Duration // default 60s
    Default   time.Duration // cooldown without Retry-After; default 5m
}
type Event struct{ ID string; At time.Time; Target alias.Target; StatusCode int; RetryAfter time.Duration } // Target in user names
type Cooling struct{ Target alias.Target; Until time.Time; Reason string } // Reason "402" | "429"
func New(cfg Config, apply func(context.Context) error, now func() time.Time, log *slog.Logger) *Cooler
func (c *Cooler) Observe(ctx context.Context, e Event) error // may call apply
```

Rules:
- A 402 cools at once.
- A 429 is counted by `e.At` inside `Window`. When the count reaches `Threshold`, the member cools.

- Other status codes are ignored.
- The 429 count of a member resets when the member is restored.
- `apply` runs outside the lock. If it fails, the error is returned and the state is kept, so the next `Expire` or reconcile pass retries.
